    31. Memory Management

    Ebo epochs, cycle collection, and cross-actor yanda

    Ifá-Lang manages memory automatically. You don't need to free or drop — but understanding how memory is managed helps you write efficient, leak-free programs.

    Three Memory Tools

    ToolWhen to UseAutomatic?
    ebo { ... }Short-lived work (iterations, requests, file processing)No — you write ebo explicitly
    Cycle collectorLong-lived cyclic data (graphs, caches, reactive networks)Yes — runs dynamically (e.g. every 512 VM ticks by default)
    yandaSending values across actorsNo — you write yanda explicitly

    1. Ebo — Your First Memory Tool

    Always start with ebo. It is the most efficient memory management strategy. All allocations inside an ebo block are freed when the block exits.

    // Bad: memory accumulates
ayanmo results = [];
fun i = 0; i < 10000; i++ {
    ayanmo chunk = fetch_chunk(i);   // allocated each iteration
    Ogbontarigi.wo(results, chunk);  // chunk stays alive
}
// 10,000 allocations waiting for GC

// Good: memory freed each iteration
ayanmo results = [];
fun i = 0; i < 10000; i++ {
    ebo "chunk" {
        ayanmo chunk = fetch_chunk(i);
        Ogbontarigi.wo(results, chunk);
    }  // chunk freed here, but results keeps its reference
}
// results has 10,000 entries but intermediate copies are freed
    Note: Values appended to results survive the ebo block because the outer scope still references them. The IfaGc reference count keeps them alive.

    2. Cycle Collection — Invisible Safety Net

    The cycle collector runs automatically at dynamic VM tick intervals depending on your configured #opon size (every 512 ticks for the default arinrin size). You usually don't need to think about it — but if you're building cyclic data structures, it prevents leaks.

    // A self-referential cycle — would leak in reference counting alone
ayanmo node = {
    "name": "root",
    "children": []
};

// Create cycle: node.children includes node itself
ayanmo children = node["children"];
Ogbontarigi.wo(children, node);
// node holds children holds node — refcount never drops to 0

// Without cycle collector: memory leak
// With cycle collector (dynamic sweep): detected and freed

    You can adjust the cycle collection frequency dynamically using opon presets:

    opon kekere;   // Collect cycle suspect buffer every 128 ticks (often)
opon nla;      // Collect cycle suspect buffer every 2,048 ticks (rarely)
    Note: The GC tuning parameters from OponSize::gc_policy() are fully wired and active in the VM. Cycle collection checks are automatically triggered on execution ticks based on your chosen #opon size. See the Opon Reference for details.

    3. Yanda — Cross-Actor Ownership

    When you send a value to another actor, it is deep-copied via serialization. The receiving actor gets a fresh copy on its own heap, isolated from the sender's GC.

    // Spawn a worker actor
ayanmo worker = ajose "worker" {
    reti msg from inbox {
        Irosu.fo("Received: " + msg);
    }
};

// Send data — deep copy across the boundary
ayanmo data = [1, 2, {"key": "value"}];
yanda data to worker;
// data is still valid here (native VM keeps the original)
// data_2 still valid here (non-destructive for native target)

// The worker operates on its own copy
// Modifications on one side don't affect the other

    4. Putting It Together

    Here's a complete example showing all three tools:

    // A web server with proper memory management
ese start_server() {
    opon nla;  // Expect large allocations
    
    ebo "server-lifecycle" {
        ayanmo server = Otura.de(":8080");
        
        fun i = 0; i < 100; i++ {
            ebo "request" {
                ayanmo conn = reti server.accept();
                ayanmo result = process_request(conn);
                
                // Spawn actor for heavy work
                ayanmo worker = ajose "worker" {
                    ayanmo data = reti msg;
                    Irosu.fo("Processed: " + data);
                };
                
                yanda result to worker;
            }  // conn and request allocations freed
        }
        
        defer { Otura.pa(server); };
    }  // server freed
}
    Rule of thumb: Use ebo for scoped work. Trust the collector for cycles. Use yanda for actor messages. You rarely need to think about memory beyond that.
