Memory Management

Opon System - Sacred Memory Management

Overview

Ifa-Lang uses a memory management system based on Opon (the divination tray/calabash). The system tracks memory allocation, provides scoped allocation epochs, and includes a flight recorder for debugging. Memory is reference-counted with a dynamically tuned tracing cycle collector (Bacon-Rajan algorithm) running at configured intervals to clean up reference cycles. The implementation lives in crates/ifa-vm/src/opon.rs and crates/ifa-types/src/gc.rs.

Opon Memory System

Opon is a Vec<IfaValue>-based memory store with configurable sizing and limit enforcement.

Memory Size Presets

// Memory size directives (use at top of file)
#opon kekere;    // 256 slots (~4KB) - embedded systems
#opon arinrin;   // 4096 slots (~64KB) - default
#opon nla;       // 65536 slots (~1MB) - large workloads
#opon ailopin;   // Unlimited (hard ceiling at 1,048,576 slots)

Memory Operations

  • get(addr): Read value at address
  • set(addr, value): Write value at address (returns bool)
  • allocate(value): Allocate next available slot
  • memory_used(): Count of non-null slots
  • Unlimited mode grows dynamically up to a 1M hard ceiling

Ebo Epoch System

Scoped allocation regions. All allocations within an epoch are released together when the epoch ends. This provides deterministic memory management without garbage collection.

// Ebo field declaration (resource with automatic cleanup)
ebo file = Odi.ka("data.txt");
// File handle released when scope ends

// In the parser/VM, ebo with a body creates a scoped memory epoch:
// All allocations within the epoch are released at scope exit

Epoch Properties

  • Each epoch has: id (monotonically increasing), name, start_addr, alloc_count, active flag
  • Nested epochs are supported (stack of active epochs)
  • On end_epoch(), memory is truncated back to the epoch's start address
  • No generational GC or mark-and-sweep — purely scope-based release

Flight Recorder

Opon includes a circular buffer for debugging and diagnostics. It records all domain method calls with spirit (domain name), action, and value.

  • Capacity: 256 events (16 x 16, a sacred number)
  • Circular buffer: oldest events are overwritten when full
  • Used by the VM for tracing and debugging
Scoping distinction: The Opon runtime flight recorder (256-event circular buffer) is a completely separate system from the 32-step compile-time StateHistoryBuffer. While the flight recorder tracks domain events at runtime for logging and debugging, the StateHistoryBuffer operates during static analysis in the Babalawo linter to provide time-travel diagnostics for borrow checking.

IfaValue Memory Layout

Based on the tagged union implementation in crates/ifa-types/src/value_union.rs:

// Tagged union layout — 16 bytes on 64-bit
pub enum IfaValue {
    Null,                       // 0 bytes (discriminant only)
    Bool(bool),                 // 1 byte + padding
    Int(i64),                   // 8 bytes
    Float(f64),                 // 8 bytes
    Str(Box<String>),           // 8 bytes (thin pointer)
    List(IfaGc<Vec<IfaValue>>),// 8 bytes (pointer)
    Map(IfaGc<HashMap<...>>),  // 8 bytes (pointer)
    Fn(Arc<BytecodeFnData>),   // 8 bytes (pointer)
    Result(Box<ResultPayload>),// 8 bytes (pointer)
    Resource(Arc<ResourceToken>),// 8 bytes (pointer)
    // VM-specific variants follow the same pattern
}

CompactString (Map Keys)

  • Used for HashMap<CompactString, IfaValue> map keys
  • Inline branch: { len: u8, char_len: u8, data: [u8; 21] } — strings up to 21 bytes stored inline
  • Heap branch: Arc<str> — strings over 21 bytes

Memory Safety

Reference Counting & Cycle Collection

  • List, Map, Fn, Resource use IfaGc<T> or Arc<T> for shared ownership
  • Automatic deallocation when refcount reaches 0
  • Bacon-Rajan cycle collector checks for and collects cycle suspects at dynamic tick intervals configured by #opon size

Bounds Checking

  • All array/list access is bounds-checked at runtime
  • Type checking for operations (TypeError on mismatch)
  • Resource handle validation

Opon Exhausted

  • When memory limit is hit, OponExhausted error is raised
  • Includes requested and available counts for debugging

Best Practices

Memory Configuration

  • Use #opon kekere for embedded/bare-metal targets
  • Use #opon arinrin for most applications (default)
  • Use #opon nla for data-intensive workloads
  • Use #opon ailopin for development (capped at 1M slots)

String Efficiency

  • Strings up to 21 bytes incur zero heap allocation
  • Longer strings share data via Arc (copy-on-write by refcount)
  • Prefer short identifiers and keys

Resource Cleanup

  • Use ebo keyword for resources that need automatic cleanup
  • Resources are released when their scope exits
  • Ebo epochs provide scoped bulk deallocation
