Language Internals

Architecture & Implementation Details

This section documents the internal architecture of Ifa-Lang for contributors and advanced users, based on the actual codebase implementation.

Runtime Architecture

Ifa-Lang implements a compilation pipeline: parser (ifa-parser, pest grammar + logos lexer) to AST to bytecode (ifa-compiler) executed by IfaVM (ifa-vm). Two execution paths exist: tree-walking interpreter (ifa-interpreter) and bytecode VM (ifa-vm). Both parse and compile via the same pipeline.

IfaParser

Logos + Pest grammar definition. Produces AST.

Source: crates/ifa-parser/

IfaCompiler

AST to bytecode compilation.

Source: crates/ifa-compiler/

IfaVM

Bytecode VM with step() dispatch loop, Opon epoch memory system.

Source: crates/ifa-vm/

IfaInterpreter

Tree-walking AST interpreter (alternative execution path).

Source: crates/ifa-interpreter/

IfaTranspiler

AST to Rust code generation for native compilation via ifa build.

Source: crates/ifa-transpiler/

IfaVM Architecture

The bytecode VM (crates/ifa-vm/src/) is structured as:

  • vm.rs — Main VM with step() dispatch loop
  • opon.rs — Opon epoch memory system (calabash, slot-based storage with history recording)
  • vm_ikin.rs — VM optimization/acceleration
  • actor.rs — Actor model (spawned VMs share no state)
  • native/ — OduRegistry trait for domain dispatch

IfaValue (32-byte Tagged Union)

IfaValue is a 32-byte tagged union with SSO (small-string optimization) up to 21 bytes. Uses Arc<Mutex> (not Rc<RefCell>) for shared mutable state and Arc<str> for strings. IfaShared uses Arc<RwLock> and DashMap for Send+Sync concurrency.

Source: crates/ifa-types/src/value_union.rs

Opon Memory System

Opon (calabash) is the epoch memory system. It provides:

  • Slot-based storage with get/set operations
  • History recording (record/record_msg) for domain calls
  • Embedded mode for smaller history on constrained targets
  • OponError/OponErrorKind for error handling
  • OponSize for capacity management

Standard Library Registry

The StdRegistry in crates/ifa-std/src/vm_registry.rs implements the OduRegistry trait for domain dispatch. Domain IDs:

  • 0 = Ogbe, 1 = Oyeku, 2 = Iwori, 3 = Odi, 4 = Irosu
  • 5 = Owonrin, 6 = Obara, 7 = Okanran, 8 = Ogunda
  • 9 = Osa, 10 = Ika, 11 = Oturupon, 12 = Otura (backend)
  • 13 = Irete (crypto), 14 = Ose (game), 15 = Ofun
  • 18 = CPU, 19 = GPU, 20 = Storage, 29 = Sys

Each domain has a dispatch function matching method names (with aliases) to handlers. Stateless dispatchers exist for Ogbe, Oyeku, Iwori, Owonrin, Obara, Okanran, Ogunda, Osa, Ika, Oturupon, Ofun. Stateful dispatchers (needing Esu/Esu) exist for Odi, Irosu, Otura, Irete.

Feature Flag System

Granular feature flags control domain availability:

  • Always-available: ogbe, oyeku, iwori, irosu, owonrin, obara, okanran, ogunda, ika, oturupon, ofun
  • Gated: odi/osa/otura (backend), ose (game), irete (crypto)
  • Stacks: crypto, backend, frontend, gamedev, ml, iot, fusion
  • Infra: ffi (polyglot), cpu (parallel), gpu (wgpu), storage (tokio+persistence), sys (sysinfo)
