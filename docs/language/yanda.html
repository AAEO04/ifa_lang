    Yanda — Ownership Transfer & Memory Model

    Deep-copy semantics for cross-actor messaging (Yoruba: yanda = surrender/release)

    1. Memory Management Overview

    Ifá-Lang uses automatic memory management with two complementary strategies:

    StrategyKeywordScopeDescription
    Epoch reclamationebo { ... }Block-scopedAllocations released at scope exit — primary strategy
    Cycle collectionAutomaticVM-wideBacon-Rajan collector handles long-lived cycles every 1024 VM ticks
    Ownership transferyandaCross-actorDeep-copy serialization at actor boundaries

    Memory is managed per-actor (Orí model). Each actor VM has an isolated heap. GC pointers never cross thread boundaries.

    2. Yanda — Deep-Copy Transfer

    The yanda keyword (Yoruba: "surrender/release") explicitly transfers ownership of a value across an actor boundary. Unlike Rust's move (which is zero-copy pointer handoff), Ifá-Lang's yanda is always a deep copy — the value is serialized, sent, and deserialized on the receiving actor's heap.

    // Spawn an actor
ayanmo worker = ajose "worker" {
    reti msg from inbox {
        Irosu.fo("Got: " + msg);
    }
};

// Send a value — deep-copied via serialization
ayanmo data = [1, 2, 3, [4, 5]];
yanda data to worker;
// data is still usable here (yanda is a copy for cross-actor,
// not a destructive move like Rust's)
// But for embedded targets without GC, yanda IS destructive:
// data becomes null after yanda
    Why deep copy? Each actor has its own cycle collector heap. A zero-copy pointer handoff would require cross-thread GC coordination, defeating the purpose of per-actor isolation. Serialization is the clean boundary.

    2.1 How It Works

    1. Sender calls bincode::serialize(&value) — converts IfaValue to Vec<u8>
    2. Serialized bytes are sent through a bounded SyncSender channel
    3. Receiver calls bincode::deserialize(&bytes) — allocates fresh IfaGc handles on the receiver's heap
    4. Original value remains valid on the sender (in the native VM)

    Variants that cannot be serialized (Fn, Closure, Actor, Future) are rejected at serialization time — you can't yanda a closure to another actor.

    2.2 The Serialization Bridge: IfaValueSurrogate

    yanda uses IfaValueSurrogate (value_union.rs) as the intermediate representation between IfaValue and bincode bytes. The surrogate enum mirrors the serializable subset of IfaValue:

    Surrogate VariantCorresponding IfaValueSerializable?
    NullNullYes
    Bool(bool)BoolYes
    Int(i64)IntYes
    Float(f64)FloatYes
    Str(String)StrYes
    List(Vec<IfaValue>)ListYes
    Map(HashMap<String, IfaValue>)MapYes
    Set(HashSet<IfaValue>)SetYes (added)

    2.3 Yanda and Storage — Same Serialization Path

    The Storage domain (infrastructure/infra/storage.html) uses the exact same bincode / IfaValueSurrogate serialization as yanda:

    // Both use the same serialization mechanism:
//
// yanda:   IfaValue → IfaValueSurrogate → bincode → Vec<u8> → channel
// Storage: IfaValue → IfaValueSurrogate → bincode → Vec<u8> → append-only log
//
// The same variant restrictions apply to both:
//   ✅ Serializable: Null, Bool, Int, Float, Str, List, Map, Set
//   ❌ Rejected:    Fn, Closure, Actor, Future

// yanda sends an actor message
yanda data to worker;

// Storage persists the same data
reti Storage.set(store, "cache:key", data);

    This means if a value can be yanda'd, it can also be stored in Storage, and vice versa. The Set variant was added to the surrogate specifically to enable this cross-cutting serialization.

    3. Ebo — Memory Epochs

    The ebo keyword creates a scoped memory region. All allocations within an ebo block are released when the block exits. This is the primary memory management strategy — far more efficient than cycle collection for short-lived data.

    // Without ebo: allocations live until the GC collects them
fun process_requests() {
    fun i = 0; i < 1000; i++ {
        ayanmo data = fetch_data();   // New allocation each iteration
        process(data);
        // data stays alive until GC runs
    }
}

// With ebo: allocations released at scope exit
fun process_requests() {
    fun i = 0; i < 1000; i++ {
        ebo "iteration" {
            ayanmo data = fetch_data();
            process(data);
        }  // ← data freed here
    }
}

    4. Opon — Memory Subsystem

    The #opon directive (the divination tray) configures Ifá-Lang's slot-based memory store. Opon controls slot capacity, stack depth, and frame nesting limits. It also powers the ebo epoch system and the flight recorder. See the dedicated Opon reference for full details.

    The OponSize::gc_policy() method defines GC tuning parameters, but these are aspirational — the VM currently uses a hardcoded 1,024-tick collector interval regardless of the #opon setting. The primary role of #opon is memory capacity and limit enforcement, not GC tuning:

    DirectiveSlotsStack CapFrame CapGC Policy
    opon kekere25625664Check every 128 ticks (unwired)
    opon arinrin4,0964,096512Check every 512 ticks (unwired)
    opon nla65,53665,5364,096Check every 2,048 ticks (unwired)
    opon ailopinDynamic up to ~1MNoneNoneCheck every 4,096 ticks (unwired)
    Note: The gc_policy() values are defined but not wired into the VM's cycle collector loop. For deterministic memory release, use ebo epochs — they always work regardless of GC tuning status.

    5. Embedded Targets (.yanda() method)

    When transpiling to embedded targets (no_std, no alloc), the yanda keyword generates a .yanda() method call. On embedded, yanda is destructive — the source value becomes null to prevent use-after-free.

    // Ifá-Lang source:
yanda data to worker;

// Transpiled to Rust (embedded target):
worker.send(data.yanda());  // yanda() consumes self, returns serialized bytes
// data is no longer valid here
