    — Opon — The Memory System

    Slot-based memory store, scoped allocation epochs, and flight recorder

    Source-verified. This page documents the Opon implementation at crates/ifa-vm/src/opon.rs and its integration in the compiler, parser, and VM.

    What is Opon?

    Opon (the divination tray / calabash) is Ifá-Lang's deterministic memory subsystem. It is a Vec<IfaValue>-based slot store with configurable sizing, limit enforcement, scoped allocation epochs, and a built-in flight recorder for debugging.

    Opon serves two distinct roles:

    • Slot memory store — a fixed-capacity array of IfaValue slots for Load/Store bytecode operations. The size determines how many values can be stored at addressed memory locations.
    • Stack and frame limit governor — the chosen OponSize sets caps on the execution stack depth and call-frame nesting, preventing runaway recursion or deep call chains from exhausting host memory.

    OponSize Variants

    Four memory profiles control the slot capacity, execution limits, and GC tuning.

    Directive Slots Memory Stack Cap Frame Cap Use Case
    #opon kekere 256 ~4 KB 256 64 Embedded (ESP32, STM32, RP2040)
    #opon arinrin 4,096 ~64 KB 4,096 512 DEFAULT General purpose
    #opon nla 65,536 ~1 MB 65,536 4,096 Data-intensive workloads
    #opon ailopin Dynamic (up to 1,048,576) Dynamic None None Development / no limits

    English aliases are also accepted: small / tiny / embedded for kekere; medium / standard / default for arinrin; large / big / mega for nla; unlimited / dynamic / infinite / max for ailopin.

    Syntax

    Place the directive at the top of your file. Multiple forms are accepted:

    Directive Forms
    // Hash-prefix (recommended)
#opon kekere;
#opon nla;

// Colon syntax
opon: arinrin;
opon: ailopin;

// English aliases
#mem small;
mem: unlimited;

// No semicolon (also accepted)
#opon nla
opon: arinrin
    Compiler metadata only. The #opon directive is a compile-time annotation that sets the Bytecode.opon_size field. No bytecode is emitted for the directive itself. The VM reads the field during execute() to derive stack and frame limits.

    What Opon Controls

    1. Slot Memory

    The internal Vec<IfaValue> is pre-allocated to the slot count for Kekere, Arinrin, and Nla. In Ailopin mode, it starts at 1,024 slots and grows dynamically as allocations are made, up to a hard ceiling of 1,048,576 slots (AILOPIN_HARD_LIMIT).

    Slot operations are exposed through Load/Store bytecode opcodes:

    • get(addr: usize) -> Option<&IfaValue> — read from slot. Returns Null if address is out of bounds.
    • try_set(addr, value) -> OponResult<()> — write to slot. Auto-grows in Ailopin mode; returns OponExhausted if at capacity and not unlimited.
    • allocate(value) -> OponResult<usize> — allocate the next free slot and return its address.

    2. Stack & Frame Limits

    The chosen OponSize determines execution safety limits:

    • Stack limit — max depth of the operand stack. Exceeding it raises IfaError::StackOverflow with a message like "program declared #opon arinrin (limit: 4096 slots)".
    • Frame limit — max depth of call-frame nesting. Prevents runaway recursion from consuming host memory.

    3. GC Tuning ASPIRATIONAL

    Each OponSize defines a gc_policy() that returns tuning parameters for the cycle collector:

    SizeCheck Interval (ticks)Suspect Threshold
    Kekere1288
    Arinrin51232
    Nla2,048128
    Ailopin4,096256

    Currently the VM uses a hardcoded 1,024-tick interval for cycle collection — the gc_policy() values are not yet wired into the GC loop. The Ebo epoch system provides the primary deterministic memory release; the cycle collector is a fallback for cyclic List/Map structures that cannot be freed by reference counting alone.

    Ebo Epoch System

    Opon supports scoped allocation regions called epochs, created by the ebo statement with a body:

    Scoped Epoch
    ebo "request" {
    // All allocations within this block are tracked
    ayanmo data = fetch_data();
    process(data);
}  // ← epoch ends here: memory truncated back to epoch start

    Internally, begin_epoch(name) takes a snapshot of the current memory length, and end_epoch() calls memory.truncate(start_addr) to release all allocations in one shot. Epochs support nesting (stack-like):

    ebo "connection" {            // epoch id=1, start at slot 100
    ayanmo conn = open();
    ebo "query" {             // epoch id=2, start at slot 110
        ayanmo result = run(conn);
    }                         // truncated back to slot 110
    // result is gone, conn still valid at slot 102
}                             // truncated back to slot 100

    Each epoch records: id (monotonically increasing), name (human-readable), start_addr (first allocation), alloc_count, and an active flag.

    Flight Recorder (Spirit Log)

    Opon includes a 256-event circular buffer that records domain operations. Every Print, PrintRaw, Input, and Store* operation is logged with:

    • Spirit — the domain name (e.g., "Ìrosù", "Ogbè", "MMIO")
    • Action — the operation (e.g., "fọ (spoke)", "gbà (received)", "write")
    • Value — the value involved (string representation)
    • Epoch ID — which epoch was active when the event occurred
    # Retrieve flight recorder data
ayanmo log = opon.get_history();
// Returns events ordered chronologically, oldest first

    The flight recorder is used by the WASM bindings to stream "Spirit Logs" to the browser playground UI. The capacity of 256 events is a sacred number (16 × 16). Oldest events are overwritten when the buffer wraps.

    Errors & Troubleshooting

    OponExhausted

    Raised when an allocation exceeds the slot capacity for the chosen size:

    Opon (memory) exhausted: requested 257, available 256
→ Hint: Use '#opon nla' or '#opon ailopin' for more capacity.

    What to do:

    • Switch to a larger #opon size (nla gives 65,536 slots)
    • Use ebo epochs to release memory between phases
    • Use #opon ailopin during development, then profile and choose the tightest size that works for your production workload
    • Check for unbounded allocation in loops — you may have a leak

    StackOverflow

    Raised when the operand stack or call-frame nesting exceeds the limit:

    stack overflow — program declared #opon arinrin (limit: 4096 slots)

    What to do:

    • Increase #opon size (nla lifts stack cap to 65,536)
    • Use #opon ailopin to remove limits entirely
    • Check for infinite recursion or deeply nested match statements

    Relationship with the Cycle Collector

    Ifá-Lang has two memory management mechanisms that work independently:

    Opon (deterministic)Cycle Collector (tracing)
    What it managesSlot store (addressed memory) IfaGc heap (List, Map, Closure)
    Release triggerEpoch end (scope exit) Every 1,024 VM ticks
    Frees cycles?No (linear truncation) Yes (Bacon-Rajan algorithm)
    Deterministic?Yes No (runs at fixed intervals)
    InteractionThe Opon epoch reduces GC pressure by freeing memory before the cycle collector runs. Fewer live objects → faster GC sweeps.
    Note on "opon as GC hint": Some tutorial sections describe opon kekere as "collect often" and opon nla as "collect rarely". While OponSize::gc_policy() does define tuning parameters for this purpose, the VM currently uses a hardcoded 1,024-tick interval regardless of the #opon setting. The primary role of Opon is slot memory and limit enforcement, not GC tuning.

    CpuOponView — Not the Same Thing

    CpuOponView is a zero-copy GPU/CPU compute buffer defined in crates/ifa-std/src/hardware/cpu.rs. Despite the shared "Opon" naming (calabash = container), it is a completely separate concept from the VM's Opon memory subsystem:

    Best Practices

    Choosing a Size

    • Embedded targets → #opon kekere (256 slots, ~4KB)
    • CLI tools, scripts → #opon arinrin (4K slots, default)
    • Data processing, servers → #opon nla (65K slots)
    • Development / unsure → #opon ailopin (no limits, but capped at ~1M slots as safety net)

    Memory Discipline

    • Use ebo "name" { ... } to scope allocations — memory is freed at epoch end regardless of GC timing
    • Nest epochs for phases of computation (e.g., one epoch per request handler)
    • Monitor memory_used() during development to choose the right size
    • Avoid unbounded allocation in tight loops — use epochs to bound lifetime

    When to Use Ailopin

    #opon ailopin removes all slot and stack limits, which is useful for: prototyping, one-shot scripts, and programs with unpredictable allocation patterns. However, consider that unlimited mode prevents the VM from catching runaway memory use early. For production, prefer a bounded size and test under load.
