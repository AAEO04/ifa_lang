    GC Invariants & Thread Safety

    Architectural rules every maintainer must know

    Source-verified. Extracted from crates/ifa-types/src/gc.rs, crates/ifa-vm/src/actor.rs, crates/ifa-types/src/bytecode.rs, crates/ifa-types/src/lib.rs.

    1. Non-Negotiable Invariants

    Violating any of these causes undefined behavior. No exceptions.
    1. IfaGc is !Send and !Sync. gc.rs:62 — PhantomData<*mut ()> enforces this at the type level. Never add unsafe impl Send to IfaGc. Threads must use serialized Vec<u8> to communicate.
    2. Every actor has its own suspect buffer. gc.rs:47-49 — thread_local! { SUSPECT_BUFFER: RefCell<Vec<...>> }. The Bacon-Rajan collector runs in the actor's own thread and only drains that actor's suspects.
    3. Drop returns early for Color::Red. gc.rs:136-138 — When the collector is dismantling a cycle, it sets color to Red. The Drop impl checks this and returns immediately to prevent double-free.
    4. Buffered invariant. A node in the suspect buffer always has strong >= 1 (the buffer holds its own reference). A node at strong == 0 can never be in the buffer.
    5. The prev == 1 fast path must never clone. gc.rs:143-150 — When strong count drops to 0 and the node is not buffered, it is freed immediately. This path must not interact with the suspect buffer.
    6. Clone resets color to Black. gc.rs:123 — h.color.set(Color::Black). When an IfaGc is cloned, the new reference makes the node externally reachable again, cancelling any pending cycle suspicion.

    2. Bytecode Shared Constant Pool

    bytecode.rs:82-85:

    // SAFETY: Bytecode constants only contain primitives and strings (no IfaGc cycles).
unsafe impl Send for Bytecode {}
unsafe impl Sync for Bytecode {}
    Loaded gun. This is safe today because the compiler never emits IfaGc into the constant pool — only Int, Float, Bool, Null, and Str. If the constant pool ever gains closures or pre-baked List/Map literals, this unsafe impl becomes unsound and must be removed.

    3. Thread Boundary Architecture

    There are exactly three threading contexts in the native runtime:

    ThreadHas IfaGc?Has IfaValue?Communication
    VM (actor)Yes — per-actor heapYes — full value systembincode::serialize → channel
    Storage workerNoNo (only Vec<u8>)mpsc::SyncSender<StorageCmd>
    GPU workerNoNo (only Vec<u8>)oneshot<Vec<u8>>
    Hardware workers never hold GC pointers. If you add a new hardware module, follow the crates/ifa-std/src/hardware/storage.rs pattern: serialize at the VM boundary, deserialize on the worker, pass results back through a response channel.

    4. Feature Gating

    The IfaGc module is always compiled in ifa-types. There is no feature gate — the GC is a core architectural invariant, not an optional component.

    • gc.rs is pub mod gc at lib.rs:37 — always available
    • IfaGc variants in IfaValue (List, Map, Closure, Upvalue) are always present
    • The gc feature was considered but rejected — gating the collector would require duplicating IfaValue variants, which is worse than the minimal code size of the compiled-but-idle collector

    5. Testing GC Code

    GC tests live in crates/ifa-vm/tests/:

    • conformance_tier1.rs — runs ifa binary against .ifa files with # expect: comments
    • Cycle-specific test files in tests/ exercise cycle formation and reclamation
    • The collect_cycles() function returns the count of freed nodes — assert on this in unit tests
    // Example assertion pattern:
let freed = ifa_types::gc::collect_cycles();
assert!(freed > 0, "should have collected the cycle");

    6. Common Mistakes
